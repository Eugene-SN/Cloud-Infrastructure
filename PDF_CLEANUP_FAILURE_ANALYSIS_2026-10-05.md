Статус: диагностика завершена; исправления production не выполнялись.

Это три причины в CLI/режиме сохранения PDF. n8n передаёт сообщения и timeout;
четыре первых отказа имеют RC=3 на этапе **analyze**, до записи результата.
Они не являются RC=4 от проверки потери содержимого уже очищенного PDF.
Redfish остановлен адаптером по времени, без заключения об ошибке содержимого.

## User Guide: рисунок ошибочно считается таблицей

`core.py:83–90` считает строку табличной, если хотя бы одна позиция её символов
попадает в bounding box достаточно крупного векторного path. Геометрия path,
его назначение и clipping при этом не исследуются. `get_drawings()` возвращает
векторную графику, а не перечень подтверждённых таблиц.

На WA7780 page 46 распознан правильный номер `40`, а соседняя строка
`WA7780 G3 服務器用戶手冊` имеет практически тот же baseline: 756.674 против
756.653 pt. При расширении номера до всей строки проверка находит 11 enclosing
paths от иллюстрации сервера и выдаёт `footer candidate overlaps table text`.

На WA7785a page 34 правильный номер — `28`; соседняя строка
`WA7785a G3 服務器用戶手冊` попадает в bounding boxes девяти paths иллюстрации.
Визуально проверены полные рендеры обеих страниц: конфликтующая строка — обычный
нижний колонтитул, а не текст таблицы. Принадлежность позиции bounding box
рисунка не доказывает пересечения с его видимой графикой.

Направление исправления: уточнить определение настоящих таблиц/видимых объектов,
сохранив запрет удаления полезного текста и последующую content validation.
Глобальное отключение `within_table` не является подтверждённым исправлением.

## BIOS Guide: одиночная страница i

Оба документа имеют обложку, одностраничное оглавление с печатным номером `i`
и затем основной текст с `1, 2, 3…`. Рендеры и извлечённые координаты совпадают.
Native pagination markers на проблемных страницах отсутствуют.

`core.py:162–168` подтверждает числовую последовательность только при наличии
как минимум двух страниц с согласованным смещением физического/печатного номера.
Для единственной `i` это невозможно. Затем `core.py:180–183` обнаруживает
подтверждённые арабские номера в той же позиции и шрифте и отказывает всему PDF.
Эта последняя проверка сопоставляет шрифт, высоту страницы и baseline, но не
разделяет тип римской/арабской нумерации.

Само число `i` находится в настоящем колонтитуле оглавления; это подтверждённое
ограничение распознавания нового layout. Направление исправления — универсальное
распознавание одиночной вводной римской страницы с отдельной проверкой её
принадлежности колонтитулу. Простое удаление любого одиночного числа небезопасно.

## Redfish: сохранение, а не проверка содержимого

Файл: 8,326,662 bytes, 423 страницы, xref length 113,763; 107 Dest и 26 URI links.
Pagination rows в этом документе не обнаружены, что согласуется с handoff.
Отсутствие колонтитулов уже допускается алгоритмом: пустой `selected` не
вызывает ошибку, а блок `core.py:261` проверяет наличие всего native text layer,
не наличие колонтитулов. В данном PDF имеются 133 целевые кликабельные ссылки;
по действующему контракту cleanup удаляет их даже при нуле колонтитулов.
Буквальное побайтовое копирование сохранило бы эти ссылки. Быстрый copy/no-op
путь без изменения контракта применим, когда отсутствуют **все** цели очистки,
а не только pagination rows. Изменение этого поведения не внедрено.
История n8n execution 12232 показывает `Cleanup exceeded 900 seconds` и
длительность CLI-узла 906,117 ms с учётом остановки контейнера.

В отдельном диагностическом процессе неизменённый алгоритм завершил
`inspect_pdf` за 33.666 s и `analyze` за 13.569 s. Три последовательных снимка
стека далее показывали `core.py:291 -> Document.save -> pdf_save_document`.
Этот контрольный процесс остановлен вручную после получения повторных снимков;
его остановка не выдаётся за второй полный 900-секундный timeout.

Контролируемый эксперимент изменил **один параметр только в памяти отдельного
процесса**: `garbage=3` → `garbage=2`. Установленный core, guard, image и runtime
не изменялись. Оригинал смонтирован read-only, весь результат находится в `/tmp`.

- сохранение завершилось за **0.476 s**;
- полный cleanup с неизменённой штатной validation завершился за **88.693 s**;
- все 423 страницы прошли проверку текста/координат, геометрии, изображений,
  векторной графики, bookmarks и оставшихся аннотаций;
- удалены 133 целевые ссылки; колонтитулов и widgets не удалялось;
- original SHA256 сохранился;
- тестовый результат имеет 17,340,426 bytes: этот быстрый режим в текущих
  остальных настройках увеличивает файл примерно вдвое. Это материал для
  выбора режима сохранения, а не уже внедрённая оптимизация.

Официальный контракт PyMuPDF: level 2 удаляет неиспользуемые объекты и уплотняет
xref, level 3 дополнительно объединяет дубликаты. Исходники точного MuPDF 1.28.2
содержат вложенное сравнение объекта с предшествующими объектами в
`removeduplicateobjs`. В сочетании с повторными стеками и экспериментом это
подтверждает причину дорогостоящего сохранения данного большого object graph.
Простое увеличение timeout не устраняет эту причину.

## Границы результата и сохранность

Подтверждены причины **первых** отказов четырёх руководств. Исправленная обработка
всего этих PDF ещё не проверялась: после устранения первого отказа могут
обнаружиться другие неподдерживаемые страницы. Для Redfish подтверждено полное
прохождение штатных проверок при описанном диагностическом режиме сохранения.

Production CLI, launcher, adapter, image/tag, n8n workflows, cloud originals,
cleaned и INDEX.html этой диагностикой не менялись. SHA256 всех пяти originals
проверены до/после. Тестовые PDF, рендеры, временные рабочие файлы и диагностические
контейнеры удалены после сохранения не содержащих секретов доказательств.
