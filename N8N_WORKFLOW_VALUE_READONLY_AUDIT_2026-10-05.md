# n8n workflow value — read-only audit, 2026-10-05

**Status: READ-ONLY RESEARCH. Recommendations and alternatives below are proposals, not accepted architecture or authorization to change anything.** Accepted products are retained. This document evaluates workflow purpose; it does not reopen product selection.

## Итог расширенного исследования для оператора

**Не все десять workflows одинаково нужны.** Два workflows обслуживают конкретную библиотеку Lenovo, два предоставляют агентам инструменты, три образуют связанный контур уведомлений Plane, а у оставшихся трёх текущая прикладная польза не подтверждена. Рекомендация — рассмотреть удаление GitHub-пары и Nextcloud event ingress, сохранив остальные семь по их текущим ролям. Это предложение, не принятое решение об удалении. За этот аудит ничего в runtime не изменено.

### Зависимости и реальные альтернативы

**CONFIRMED FACT:** опубликованные прямые subworkflow calls — `PlaneGitHubPoll01 → PlaneGitHubSync01` и `TechnicalDocumentationSync → LenovoPdfCleanup`. Plane notifications связаны через свои native inbox/state tables. Nextcloud event inbox не участвует в этих цепочках. На текущем срезе опубликованные версия и draft совпадают для всех десяти workflows.

**INFERENCE:** семь workflows имеют конкретную текущую или принятую инструментальную роль: документная пара, два agent tools, три Plane notification components. Сохранение Plane-тройки основано на уже принятой функции уведомлений, а не на доказанном трафике за эти три дня. Если нужен только технический минимум работы сервисов, такие пользовательские уведомления необязательны; их удаление меняет полезную функцию, а не исправляет неисправность.

**CONFIRMED FACT / upstream:** Nextcloud предоставляет WebDAV и OCS; Mattermost умеет принимать сообщения; Plane CE source поддерживает webhook и native activity. **INFERENCE:** из этого не следует, что готовая прямая интеграция заменит текущие фильтры, mapping, дедупликацию и подтверждение удаления. Сокращение workflows не требует внедрения нового продукта. Native Nextcloud Context Agent MCP требует дополнительных компонентов и не является установленной бесплатной заменой этих двух n8n adapters по имеющимся данным.

### Цена текущих расписаний и граница наблюдения

**CONFIRMED FACT:** 30-second Mattermost schedule даёт 2 880 runs/day; 5-minute reconciliation — 288; 15-minute GitHub poll — 96. Итого **3 264 scheduled runs/day**, без ежедневной синхронизации и других запросов. Reconciliation делает сейчас по семь item activity reads/run, то есть примерно 2 016 item reads/day при неизменном cache; pagination может добавить HTTP calls. Retained successful execution JSON этих трёх workflows содержит около 123 MiB по native `jsonSizeBytes`; это не размер будущего бэкапа и не оценка потреблённого CPU. SQLite file на срезе — 144 019 456 bytes; эти величины не складываются.

**CONFIRMED FACT:** установленный n8n executions config задаёт штатные `pruneData=true`, `pruneDataMaxAge=336` часов и `pruneDataMaxCount=10_000`. В container environment нет overrides `EXECUTIONS_DATA_*`. **INFERENCE:** при таком потоке count limit достигается примерно за 10 000 / 3 264 = **3,06 суток**, раньше age limit. Чистка выполняется штатно периодически, поэтому фактическая граница не обязана быть ровно 10 000 строк или ровно 3,06 суток. Опросы сокращают видимую историю других инструментов; низкий счётчик сохранённых запусков нельзя использовать как самостоятельный критерий удаления.

**UNKNOWN:** CPU/network cost без отдельного измерения. Перегрузка не установлена. Совпадение текущей частоты с желаемой задержкой уведомлений — выбор оператора, не требование продуктов. Возможные будущие изменения частоты или сохранения успешных executions требуют отдельного решения и не выполнены в этом аудите.

**CONFIRMED FACT / опубликованный контракт документной работы:** cleanup уже проверен на двух существующих PDF; остальные 76 не поставлены автоматически на массовую обработку. OCR и перевод не реализованы. При ошибке cleanup originals и INDEX уже сохранены; следующий sync не повторяет очистку неизменившегося source автоматически. **INFERENCE:** практический предел полезной документной цепочки сейчас — сопровождение originals и очистка новых/изменённых PDF при успешном child run; это ещё не полностью очищенный и переведённый корпус. Неуспешную очистку требуется повторно вызвать для соответствующих путей. Новая очередь/retry либо массовая обработка не предлагаются как автоматически принятые изменения.

## What the n8n connection actually supplies

**CONFIRMED FACT, current documentation:** instance MCP is one authenticated n8n connection. Running exposed workflows and authoring workflows are separate capabilities. Workflow previews can be discoverable without exposure; full access/execution requires the applicable workflow permission/exposure. Current documentation includes workflow authoring, so the historical statement that official MCP cannot build workflows is no longer generally correct. Per-workflow MCP access is not a reason to publish every scheduled infrastructure workflow. [Official connection/exposure contract](https://docs.n8n.io/connect/connect-to-n8n-mcp-server).

**Version uncertainty:** that overview dates authoring to 2.13.0, whereas the current tools reference dates `create_workflow_from_code` and `update_workflow` to 2.12.0. Determine installed availability from its reported version and tools; do not resolve the documentation discrepancy by guessing. The reference separately documents execution, validation, authoring and Data Table tools. Its current execution contract distinguishes published production and manual draft execution, and returns an execution ID for follow-up. [Official MCP tool reference](https://docs.n8n.io/connect/connect-to-n8n-mcp-server/mcp-server-tools-reference).

**INFERENCE:** `AIExecution01` and `NextcloudTools01` expose application actions. They are not prerequisites for a coding agent to connect to n8n and create or edit workflows. Removing an application tool would remove its reusable action contract, not the entire n8n builder connection. The right question is whether the operator or another workflow needs that contract.

**CONFIRMED FACT:** Execute Sub-workflow passes inputs to another workflow and can wait for its result; the final sub-workflow node returns data to the caller. A separate worker workflow therefore can be a useful internal dependency without being a separate user-facing automation. [Execute Sub-workflow](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.executeworkflow).

**CONFIRMED FACT:** Schedule Trigger supports fixed intervals and cron-like schedules, requires publication, and uses workflow timezone before instance timezone. Timezone and polling frequency are operator choices rather than requirements imposed by the service being polled. [Schedule Trigger](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.scheduletrigger).

**CONFIRMED FACT:** Data Tables persist structured data across workflows and can store duplicate-prevention markers. They provide storage, not an automatically operating consumer. The current documentation describes light/moderate storage and a configurable default total limit of 200 MiB; the installed version/configuration must establish its actual limit. [Data Tables](https://docs.n8n.io/build/work-with-data/data-tables).

**INFERENCE:** calling an event table a durable inbox is justified only to the extent that successful receipt really commits a row and a consumer can process/retry it. Exactly-once effects, retention, replay, concurrency and outage recovery are properties of the workflow implementation, not guaranteed merely by using a Data Table.

**CONFIRMED FACT, upstream n8n 2.40.7:** its configuration source defaults to execution pruning enabled, maximum age 336 hours, and maximum count 10,000. Current official configuration docs describe the same controls. Installed overrides and workflow execution-saving settings determine actual retained history. [Exact 2.40.7 configuration](https://github.com/n8n-io/n8n/blob/n8n%402.40.7/packages/%40n8n/config/src/configs/executions.config.ts), [official pruning variables](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/executions).

**INFERENCE, arithmetic from supplied schedules:** 30-second, five-minute and 15-minute jobs together schedule 2,880 + 288 + 96 = 3,264 runs/day. If successful runs are saved and the 10,000 cap applies, those jobs alone fill that count in roughly 3.06 days; other runs shorten it. This is a retained-history consequence, not evidence of CPU overload. Low-frequency tools may have older runs pruned by high-frequency polling, so “no retained executions” is weaker than “never used.”

Community cannot be treated as Commercial merely because the latter can be self-hosted; paid plans require the Commercial edition. [Plane editions](https://developers.plane.so/self-hosting/editions-and-versions).

**CONFIRMED FACT:** the official self-hosted GitHub setup page is marked **Pro** and uses `/silo/api/github/...` callbacks and webhook endpoints. The phrase “Covers all plans” on that page describes GitHub Cloud's availability, not proof that Plane CE includes the integration. [Official GitHub setup](https://developers.plane.so/self-hosting/govern/integrations/github).

**CONFIRMED FACT, CE v1.4.2 source:** the CE tree retains GitHub models and frontend integration components. These artifacts do not establish a functioning native backend. ## Native delivery versus useful processing

**CONFIRMED FACT:** Mattermost can receive an HTTP POST directly through an incoming webhook when the payload matches its message contract. The URL alone is not a generic Plane-payload converter. [Mattermost incoming webhooks](https://docs.mattermost.com/integrations-guide/incoming-webhooks). n8n's supported Mattermost node can post channel messages. [Official n8n integration](https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.mattermost).

**INFERENCE:** direct posting is a practical alternative for an emitter that already formats the correct message. n8n earns its place when it adds operator-specific significance filtering, payload translation, deduplication and delayed/retried delivery. For a single operator, mirroring every action the operator just performed can be noisy; external-agent changes, failures, completions and required decisions may be more useful. This is a notification preference, not a new imposed policy. A direct Plane→Mattermost connection is not established by these sources.

**CONFIRMED FACT, Nextcloud 35 documentation:** bundled `webhook_listeners` already supplies native file events, filtering and background dispatch. The default cron cadence is five minutes unless a worker accelerates dispatch. Post-delete payloads can lack the node ID; before-events have different semantics. Event receipt is not file-content extraction. [Nextcloud 35 webhook contract](https://docs.nextcloud.com/server/stable/admin_manual/webhook_listeners/index.html).

**CONFIRMED FACT, exact v35.0.1 source:** the listener adds matching events to Nextcloud's job list. `WebhookCall` performs the HTTP request and logs unexpected statuses/exceptions without adding a retry job. `QueuedJob.start()` removes the queued entry before running it. These three files were also byte-compared against v35.0.0 and are identical. **INFERENCE:** this is native queued dispatch, not demonstrated durable replay until successful external acknowledgement. A downstream n8n inbox only protects events after they reach and are stored in n8n; it cannot recover an event never delivered to it. [Event-to-job dispatch](https://github.com/nextcloud/server/blob/v35.0.1/apps/webhook_listeners/lib/Listener/WebhooksEventListener.php), [HTTP job](https://github.com/nextcloud/server/blob/v35.0.1/apps/webhook_listeners/lib/BackgroundJobs/WebhookCall.php), [queued-job lifecycle](https://github.com/nextcloud/server/blob/v35.0.1/lib/public/BackgroundJob/QueuedJob.php).

**CONFIRMED FACT:** Nextcloud has direct WebDAV file/folder operations and an OCS sharing API, so n8n is not required for basic file access. [WebDAV](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/WebDAV/basic.html), [sharing API](https://docs.nextcloud.com/server/stable/developer_manual/client_apis/OCS/ocs-share-api.html).

**CONFIRMED FACT:** Nextcloud also documents a native Context Agent MCP server with file/share tools. It requires additional installed components: Assistant, AppAPI with a deploy daemon, and the Context Agent ExApp; using only its MCP endpoint does not require an LLM backend. **UNKNOWN:** whether those components exist here. **INFERENCE:** this is a possible upstream alternative, not a zero-cost already-installed replacement. Direct WebDAV/OCS remains the simpler information-level alternative when only file actions are wanted. [Context Agent requirements/tools](https://docs.nextcloud.com/server/stable/admin_manual/ai/app_context_agent.html), [external-client MCP usage](https://docs.nextcloud.com/server/stable/user_manual/en/ai_assistant.html).
